# price-watcher-android

Android-клиент для отслеживания цен товаров на маркетплейсах. Kotlin, Jetpack Compose, Hilt, Retrofit, многомодульный Gradle.

## Работа с задачами

- Отвечать по-русски, кратко и по существу. Перед изменениями — короткий план; после — изменённые файлы, выполненные проверки и ограничения.
- Сохранять пользовательские незакоммиченные изменения. Не делать попутных рефакторингов всего проекта и не менять форматирование несвязанных файлов.
- Подагентов не создавать без явного запроса.
- Правила относятся к новому и изменяемому коду. Старый код, который их нарушает, не повод повторять нарушение и не повод переписывать проект.
- Перед новой реализацией изучить, как аналогичная задача уже решена в проекте, и следовать этому образцу, если он не противоречит этим правилам. При конфликте правила важнее; спорный случай уточнять у пользователя.
- Новые библиотеки — только с разрешения: перед добавлением назвать библиотеку, версию и зачем она нужна.
- API бэка не менять без необходимости и объяснения.
- При замене реализации (хранилище, шифрование, формат данных, библиотека) до изменений спрашивать путь: полностью удалить старое или оставить совместимость (миграцию, очистку старых данных).

## Файлы и форматирование

- Kotlin-исходники — в `src/main/kotlin` (тесты — `src/test/kotlin`, `src/androidTest/kotlin`). Папку `java` для Kotlin не создавать.
- Каждый именованный тип — в собственном файле с совпадающим именем: class, data class, interface, enum, object, sealed-иерархии и их именованные реализации. UiState, Actions, DTO, mapper, callback и fake не держать в файле ViewModel и не вкладывать в интерфейсы.
- Допустимо в одном файле: companion object с константами, top-level функции и Preview компонента, анонимные no-op реализации для Preview.
- Kotlin Code Style: 4 пробела, без табуляции, без wildcard и неиспользуемых импортов. Длинные параметры, аргументы и цепочки Modifier — по строкам; именованные аргументы там, где это помогает читаемости.
- В XML-файлах комментарии не писать.
- Новый файл сразу добавлять через `git add <точный путь>`, без `git add .`.
- После создания или изменения файла проверять EOF: последний байт должен быть содержательным, завершающие LF/CRLF удалять. Это правило важнее настроек formatter.

## Модули

- `:app` — composition root: Application, Activity, навигация, приём внешних Intent, конфигурация окружения (адрес бэка и т.п.). Связывает фичи через callbacks.
- `:feature:<name>` — самостоятельная пользовательская функциональность (Android library): экраны, ViewModel, UI-модели, UI-мапперы, ресурсы, Preview, DI фичи. Наружу — только публичная точка входа экрана, остальное `internal`. Не создавать модуль на каждый экран или слой.
- `:core:<name>` — переиспользуемый код по ответственности: предметная логика (domain, data, DI), сетевой стек, общие асинхронные инструменты, дизайн-система. Не делать универсальную «свалку» common.
- Сетевой модуль не знает о фичах и не читает `BuildConfig` приложения; конфигурацию ему поставляет app.
- Зависимости: app → feature/core; feature → нужные core; core → другие core при необходимости. Запрещены core → feature/app, feature → feature и циклы. Фичи общаются только через app.
- Общий предметный код нескольких фич выносить в core-модуль; UI-модели остаются в фичах.
- Общие Android/Compose/Hilt-настройки — в convention plugin из `build-logic`; версии SDK/JVM и библиотек — в version catalog. В `build.gradle.kts` модуля — только namespace, особые настройки и зависимости.
- `implementation` по умолчанию, `api` — только для намеренно публичных зависимостей. Реализации помечать `internal`, публичные контракты держать минимальными. Compose не подключать к модулям без UI.
- Пустые `AndroidManifest.xml` в library не создавать.

## Архитектура

- Цепочка: ViewModel → UseCase → Repository → источники данных (сеть, локальное хранилище), Hilt-инъекция через конструкторы.
- Отдельные data-, domain- и UI-модели. Преобразования data → domain и domain → ui — явными mapper-классами в отдельных файлах. DTO не попадают в domain/UI, domain-модели — в Composable, `Response`/`HttpException` — в UI.
- Domain и data не зависят от Compose, Activity и навигации.
- Интерфейс, mapper или общий механизм вводить только при реальной ответственности.

### Безопасность

- Токены, сессии и другие секреты хранить только в зашифрованном хранилище; не держать их в `SavedStateHandle`, логах и открытых настройках.
- Не логировать токены, пароли и тела запросов/ответов с ними. Сетевое логирование — только в debug-сборке.

### Результаты операций

- Операция с несколькими ожидаемыми исходами возвращает sealed-результат с полиморфным `fun <T> map(mapper: ...Mapper<T>): T`. Контракт mapper — в domain, с методом на каждый исход, без Android/Compose.
- Ожидаемые ошибки (сеть, таймаут, неверный ввод, ответ сервера) превращать в варианты результата на границе data/domain, а не в исключения. `CancellationException` всегда пробрасывать.
- Реализация результата сама вызывает свой метод mapper. В presentation mapper создаёт конкретный UiState, делегируя преобразование данных domain → ui мапперу. Не разбирать результат через `when`/`is` в ViewModel/Composable и не сравнивать ошибки по тексту.
- Для конечного набора ошибок допустим enum, реализующий `map` полиморфно.

## ViewModel, состояние и события

- Действия экрана — небольшой интерфейс Actions в отдельном файле с методами, названными по смыслу действия, без общего `onEvent(Any)` и строковых событий. ViewModel реализует его; Screen получает контракт, а не ViewModel (ViewModel берёт только Route).
- Восстанавливаемое состояние — только в инъецированном `SavedStateHandle`: чтение через `getStateFlow(KEY, initial)`, запись `savedStateHandle[KEY] = next`. Не дублировать его в `MutableStateFlow` или полях. Ключи — `private const val` в companion object.
- Режимы экрана — отдельные неизменяемые реализации sealed interface (загрузка, контент, ошибка и т.п., только реально существующие), каждая в своём файле. Не делать один data class с `isLoading` и nullable-полями. Каждое состояние хранит только свои данные.
- Ввод формы хранить отдельным ключом `SavedStateHandle`, не копируя во все состояния.
- В `SavedStateHandle` класть только то, что сохраняется в Bundle (состояния — `Serializable`/`Parcelable`). Не сохранять Context, callbacks, Job, клиенты, большие списки и секреты.
- Допустимость события проверять в ViewModel по текущему состоянию — `disabled` у кнопки недостаточно. Переходить в загрузку синхронно до запуска корутины, затем в успех или ошибку. Без отдельных флагов блокировки и без хранения `Job` для защиты от повторов.
- `SavedStateHandle` не заменяет постоянное хранилище: долговечные данные хранит и отдаёт Repository.
- При восстановлении процесса незавершённую загрузку сбрасывать в доступное для повтора состояние или перезапускать.
- Внешний ввод (shared Intent и т.п.) во время загрузки: поведение задаётся явно — ввод не теряется молча, результат старого запроса не показывается для нового.
- Одноразовые эффекты (навигация, Toast, внешнее приложение) не повторять при recomposition и восстановлении — с явным потреблением.
- `debounce`/`flatMapLatest`/`collectLatest` — только для реальной отмены устаревших запросов, не для разовых нажатий. `Job` — только если иначе управление жизненным циклом не выразить, с объяснением.

## Асинхронность

- Асинхронную работу ViewModel запускать через общую инъецируемую абстракцию из core-модуля: работа в переданном `viewModelScope`, фон на инъецированном IO-dispatcher, результат на Main. Неожиданный сбой должен переводить экран в понятную ошибку, а не оставлять загрузку.
- Новые возможности (например, подписку на Flow) добавлять в эту же абстракцию, когда они реально понадобятся.
- Без GlobalScope и собственных scope. Подписки не запускать из recomposition или по каждому нажатию. Расположение `flowOn` выбирать осознанно.

## Compose и Preview

- Route-функция получает ViewModel через Hilt и собирает состояние через `collectAsStateWithLifecycle`; Screen принимает готовое состояние и Actions.
- UiState отображается полиморфно: каждая реализация рисует себя сама, экран вызывает её метод без большого `when`. Отрисовка не запускает сеть, навигацию и изменение состояния.
- У каждого экрана есть `@Preview`; для каждого существующего режима — отдельный Preview. Preview без Hilt, ViewModel, сети и буфера обмена: фиксированные данные, no-op Actions, тема приложения, понятное имя, `showBackground = true`. Содержательные переиспользуемые компоненты тоже с Preview.
- Строки — в resources. Цена и дата — с явными currency, locale и timezone; в Preview время фиксированное.
- Интерактивным элементам — осмысленные semantics/testTag.

## Тесты

- Тесты (unit, instrumented, UI) и fake-классы для них добавлять только по явной команде пользователя.
- Код писать тестируемым: ViewModel создаётся напрямую с `SavedStateHandle`, fake-зависимостями и fake асинхронного исполнителя, который позволяет вручную завершить операцию. Время, locale, timezone и dispatcher передавать зависимостями там, где они влияют на результат.
- По команде использовать только JUnit, без дополнительных тестовых библиотек (coroutines-test, Turbine, MockK, Mockito, Robolectric и т.п.); `runBlocking`/`CompletableDeferred` — только в тестовом коде. Без `Thread.sleep` и реальных задержек.
- Тесты сценарные: действие → проверка состояния → следующее действие. Проверять поведение, восстановление состояния, ошибки и повторные события. Fake записывают аргументы и число вызовов, каждый в своём файле. Не обращаться к реальным внешним сервисам и серверу.
